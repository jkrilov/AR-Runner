# Skill: xcodegen — shared widget source, per-platform appex targets

**When to use:** You have a WidgetKit extension that needs to ship on both iOS and watchOS, you want one source of truth for the widget code (including any `AppIntent` types it hosts), and you're driving the project from `project.yml` via xcodegen.

**Why you can't just use one shared target:** Apple's bundle-identifier validation requires that any embedded app-extension's bundle ID be **prefixed with the host app's bundle ID**. A single shared `app-extension` target with `platform: auto` + `supportedDestinations: [iOS, watchOS]` produces one `.appex` with one bundle ID — which cannot be a prefix-match for two host apps with different IDs (e.g., `com.acme.phone` and `com.acme.watch`). xcodebuild will fail at the `ValidateEmbeddedBinary` step with:

```
error: Embedded binary's bundle identifier is not prefixed with the parent app's bundle identifier.
    Embedded Binary Bundle Identifier:  com.acme.widgets
    Parent App Bundle Identifier:       com.acme.phone
```

## Pattern

Split into **two thin xcodegen targets that point at the same source directory**. They share code but each emits a properly-prefixed `.appex`.

```yaml
targets:
  AcmePhone:
    type: application
    platform: iOS
    settings:
      base:
        PRODUCT_BUNDLE_IDENTIFIER: com.acme.phone
    dependencies:
      - target: AcmeWidgetsPhone
        embed: true

  AcmeWatch:
    type: application
    platform: watchOS
    settings:
      base:
        PRODUCT_BUNDLE_IDENTIFIER: com.acme.watch
    dependencies:
      - target: AcmeWidgetsWatch
        embed: true

  AcmeWidgetsPhone:
    type: app-extension
    platform: iOS
    sources:
      - path: AcmeWidgets        # <-- shared source directory
    settings:
      base:
        PRODUCT_BUNDLE_IDENTIFIER: com.acme.phone.widgets
        PRODUCT_NAME: AcmeWidgetsPhone
        SKIP_INSTALL: YES
    info:
      path: Config/AcmeWidgetsPhone-Info.plist
      properties:
        NSExtension:
          NSExtensionPointIdentifier: com.apple.widgetkit-extension
          NSExtensionPrincipalClass: $(PRODUCT_MODULE_NAME).AcmeWidgetsBundle

  AcmeWidgetsWatch:
    type: app-extension
    platform: watchOS
    sources:
      - path: AcmeWidgets        # <-- same source directory
    settings:
      base:
        PRODUCT_BUNDLE_IDENTIFIER: com.acme.watch.widgets
        PRODUCT_NAME: AcmeWidgetsWatch
        SKIP_INSTALL: YES
    info:
      path: Config/AcmeWidgetsWatch-Info.plist
      properties:
        NSExtension:
          NSExtensionPointIdentifier: com.apple.widgetkit-extension
          NSExtensionPrincipalClass: $(PRODUCT_MODULE_NAME).AcmeWidgetsBundle
```

## Companion: gate platform-specific `WidgetFamily` values

Because the same source compiles for both platforms, gate iOS-only families (and vice versa):

```swift
.supportedFamilies(StartWorkoutWidget.supportedFamilies)

static var supportedFamilies: [WidgetFamily] {
    #if os(watchOS)
    [.accessoryRectangular]
    #else
    [.systemSmall, .accessoryRectangular]
    #endif
}
```

`.systemSmall`, `.systemMedium`, `.systemLarge` are all iOS-only. `.accessoryRectangular`, `.accessoryInline`, `.accessoryCircular` are valid on both.

## What this preserves

- **One source of truth** for widget views, providers, and any `AppIntent` types it hosts.
- **No separate AppIntents target** — the intent rides along inside the WidgetKit extension on each platform.
- **Correct bundle-ID hierarchy** — each `.appex` is properly prefixed with its host's bundle ID, so `ValidateEmbeddedBinary` passes.

## Trade-offs

- Two targets instead of one in the Xcode project (slightly more compile time).
- `Config/` ends up with two near-identical Info.plist + entitlement files generated by xcodegen — gitignore the whole `Config/` directory.
