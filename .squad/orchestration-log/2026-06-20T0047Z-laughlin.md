## Phase A Scope (PR #129)

**Coordination:** Richards (architecture), Weiss (render plan), Laughlin (implementation).

### What was built

1. **Core types** (ARRunnerCore/Sources):
   - `HUDLayoutCatalog` — versioned wrapper around custom layout array.
   - `WorkoutLayoutDefaults` — maps WorkoutType raw keys to layout IDs.
   - Both Codable/Sendable/Equatable, Linux-testable, no Apple-framework imports.

2. **HUDLayout extensions:**
   - `validated(for: WorkoutType)` — sanitizes invalid metrics → nil (renders as `--`).
   - `default(for: WorkoutType)` — per-type built-in presets.

3. **HUDLayoutResolver** (pure):
   - `activeLayout(for:defaults:catalog:)` — resolves assignment or falls back to built-in; no dangling refs.

4. **Messaging (WCMessage v6, additive):**
   - `.layoutCatalog(HUDLayoutCatalog)` case.
   - `.layoutDefaults(WorkoutLayoutDefaults)` case.
   - Schema version stays **6** (not bumped to 7); lenient decode so v6 peers decode new cases as `.unknown`.

5. **Persistence** (`Shared/Settings/HUDLayoutStore.swift`):
   - App Group `group.com.arrunner.shared` storage.
   - JSON-encoded keys `"hudLayoutCatalog"` / `"hudLayoutDefaults"`.
   - Mirrors existing `WorkoutTypePreference` pattern.

6. **Watch integration:**
   - `WatchConnectivityService` persists inbound catalog + defaults to `HUDLayoutStore`.
   - `WorkoutViewModel:808` swapped hardcoded `HUDLayout.default(for: sport)` → resolver `.validated(for: sport)`.

7. **Phone plumbing (inert):**
   - `sendLayoutCatalog(_:)` / `sendLayoutDefaults(_:)` APIs added to `WatchConnectivityService`.
   - Ready for Phase B caller; message transport gated on reachability.

### Validation

- **Linux test suite (CI):** `swift test` on Docker `swift:6.0-jammy`. **328 tests, 0 failures, 1 skipped** (+18 vs baseline 310).
- **App-target compile:** CI-gated (Windows bench has no Xcode). `ci-build` job runs all 4 schemes (watchOS + iOS, simulator + physical); all passed.
- **Code review:** Verified no Apple-framework imports in Core, SPDX headers, Swift 6 strict concurrency.

### Key decision: additive-within-v6, NOT v7 bump

**Rationale:** Preserves bi-directional compatibility with v0.6.3 peers. An old phone receiving new `.layoutCatalog` case decodes it as `.unknown` → silently ignored, no mirror regression. A new watch receiving old `v6` messages (missing catalog/defaults) decodes as expected. Version bump to v7 would have forced either a hard incompatibility wall or dual-decode-path logic; additive-within-v6 is cleaner.

### Deployment risk: inert for users with no customs

Phase A is shipped as-is to TestFlight. Users see zero UI change; all resolver calls return built-in defaults until Phase B ships the editor. Behavior is **byte-identical** for existing workouts. Low risk.

1. **Width warning = conservative + non-blocking.**
   - Line-1-right slot (most constrained, ~83px budget, ~4 font-2 glyphs).
   - Warning caption if heuristic exceeds threshold.
   - Saving never blocked; user choice.
   - Comment: // TODO(bench): calibrate on hardware.

2. **No-duplicate metric rule.**
   - Editor UI disables already-assigned metrics in picker.
   - Assigning a metric to one slot clears any existing assignment.

   - Invalid metrics for an assigned `WorkoutType` surface caption ("Speed isn't shown for Indoor Running — appears as `--`").

   - Enforced on `.onCreate` and `.onDuplicate`.
   - Tested via `HUDLayoutsViewModelTests`.
   - Replace-by-id always allowed (necessary for edit-in-place).

5. **Delete prunes assignments.**
   - When a custom layout is deleted, any `WorkoutLayoutDefaults` entries pointing to it are pruned.
   - Both catalog + defaults synced to watch after delete.

## Risks & Mitigations

### R1: Line-1-right overflow (medium)
**Risk:** User assigns a metric with long unit/format (e.g., "Distance (mi)") to the constrained slot 1; glyphs overflow, text rendered off-screen.  
**Mitigation:** Conservative width heuristic + amber warning (not a hard block). Guidance in UI + // TODO comment for post-ship bench spike.

### R2: Old watch receives new layouts (low)
**Risk:** v0.6.3 watch sees v0.6.4 phone send `.layoutCatalog` via WCMessage; unknown case → silently ignored.  
**Mitigation:** Intended. Phase A design ensures old watch ignores catalog + continues using built-in defaults (safe fallback). No regression of live mirror.

### R3: Metric validity per type (low)
**Risk:** Editor assigns "Speed" (cycling-only metric) to a layout used by multiple types; running user sees `--` instead of speed.  
**Mitigation:** By design. Editor shows warn caption for invalid metric/type combo; watch renders `--`. User is informed (caption on phone) and experience is documented (always `--` for unsupported metric).

## Lessons

1. **CI-blind-spot lesson:** WCMessage struct additions (new cases) are caught only by `ci-build` on macOS, not by Linux `swift test` (Core compiles fine; app-target linking required to expose the issue). Similarly, SwiftUI `navigationDestination(item:)` + `Set` conformance (Hashable) is CI-only. No workaround available short of installing Xcode on the bench; mitigated by disciplined pre-push review of related code patterns.

2. **Additive-within-version strategy:** Adding new optional WCMessage cases while keeping `schemaVersion` unchanged is backward-compatible and cleaner than version bumps for opt-in features. Peers with no new logic simply ignore new cases (decoding to `.unknown`); no forced upgrade. Applies well to feature-flags and opt-in capabilities.

3. **Phasing inert backend separately:** Shipping Phase A (no UI) before the editor allowed Richards and Weiss to validate architecture in isolation, and let Laughlin's watch code land independently. Phase B then plugged into proven APIs. Reduced risk vs. shipping both at once.
