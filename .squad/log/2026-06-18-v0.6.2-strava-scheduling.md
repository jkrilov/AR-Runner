# 2026-06-18 — v0.6.2 Strava Upload Autonomous Scheduling Implementation

## Session Narrative

**PR:** #125 / **Commit:** d01b033 / **Tag:** v0.6.2-1

### Problem

Field report (Joe): a 3.25mi run stuck in "uploading" forever even when the app was foregrounded. The upload had succeeded on Strava (server confirmed), but the watch UI showed no progress.

Root cause: v0.6.1's `StravaUploadQueue` had orphaned the entry in a `.uploading` state. Once an entry transitioned to `.uploading`, the `pickNext()` loop never re-selected it (only `.pending` entries were considered). With no watchdog and no autonomous re-drive, the orphaned entry stayed frozen.

### Implementation (Laughlin)

**Four-part fix:**

1. **Autonomous self-rescheduling drain** — Added `scheduleNextDrain()` to arm exactly one `Task` per process cycle, computing `nextDueDate` from backoff policy and current state. Pattern: `@ObservationIgnored private var drainTask: Task<Void, Never>?`, stored/cancelled on each transition. Deinit cancels to prevent resource leak.

2. **120s upload watchdog** — If `.uploading` state lasts >120s without a completion callback, a timer fires, the entry reverts to `.pending`, and the next drain cycle re-attempts. Prevents hanging indefinitely on bad networks or midair backgrounding.

3. **Reclaim orphaned entries** — Pure function `reclaimOrphans()` rewrites any persisted `.uploading` → `.pending` at init time. Leverages Strava's idempotency: duplicate POST with the same `external_id` (HKWorkout UUID) returns 409 Conflict → accepted as success.

4. **Visible status/error in History UI** — New `.processing` state renders as "Uploading…" or error details. Users see the queue state without guessing; errors are visible and actionable.

### State-Machine Guarantee

- `pickNext()` selects **both** `.pending` and `.processing` entries.
- No persisted state is unreachable.
- Backward-compat: existing queue files decode via optional `confirmPollCount: Int? = nil`.

### Key Lesson

**Phone unit tests are NOT executed in CI.** The `ci-build` workflow runs `build`, not `test`, and there's no Xcode or device on the dev bench. This gap allowed a phone-runtime bug (the upload scheduling loop) to ship past CI. 

**Mitigation strategy:** Keep upload-queue logic on pure/injectable seams (easy to unit-test in ARRunnerCore), and **lean on visible-error UI for field diagnosis.** A stuck entry now shows "Failed: …" instead of silent hanging, so users can report actionable context.
