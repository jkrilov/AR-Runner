## Problem Statement

Long runs (e.g. 3.25 mi) were uploading to Health but stuck in `.uploading` state, never reaching Strava. Smaller test runs uploaded fine. Root cause: `StravaUploadQueue.uploadOne` persisted entries as `.uploading` BEFORE awaiting the actual URLSession upload. When iOS suspended/killed the backgrounded app mid-upload (especially large TCX over cellular), the orphaned `.uploading` entry could never be reclaimed because `pickNext()` only selected `.pending`.

## Solution

Three-part fix establishing an unreachable-state-free state machine:

### Part 1: Reclaim Orphans at Init
- New `StravaUploadQueue.reclaimOrphans` (pure, unit-tested) scans persisted `.uploading` entries and rewrites them to `.pending` at queue initialization.
- No retry count consumed; the entry is fresh for `pickNext()`.
- Idempotency via `external_id` (= `HKWorkout.uuid`) ensures 409-duplicate detection at re-POST.

### Part 2: Background URLSession
- New `BackgroundStravaUploadTransport` conforms to `StravaUploadTransport` protocol.
- Background config: `com.arrunner.phone.strava-upload`, `isDiscretionary=false`, `sessionSendsLaunchEvents=true`.
- Multipart body written to temp file (byte-identical to in-memory construction).
- File-based `uploadTask(with:fromFile:)` survives app backgrounding.
- Delegate bridges callbacks to `async` via `CheckedContinuation` keyed by `taskIdentifier`.
- Polling (GET status checks) uses separate ephemeral session (background sessions can't run data tasks).
- `PhoneAppDelegate` hooks `handleEventsForBackgroundURLSession` completion handler and re-attaches session on background launch.

### Part 3: Confirmation Processing
- New `.processing` state for entries with 2xx POST but null `activity_id` (Strava is processing asynchronously).
- Polls `checkUploadStatus` (previously dead code) with bounded backoff: `[2, 5, 10, 20, 30]s` and max 12 confirmation attempts.
- Outcomes:
  - `activity_id` returned → `.completed`
  - Non-empty `error` → `.failed`
  - Budget exhausted → back to `.pending` (re-POST → 409 dup → completed)
  - 409 dup with no pollable ID → `.completed`

## State-Machine Invariant

`pickNext()` selects both `.pending` and `.processing`. Orphaned `.uploading` entries are reclaimed at init. **No persisted state is unreachable.**

## Backward Compatibility

- Added `confirmPollCount: Int? = nil` to `StravaUploadQueueEntry` (optional, uses `decodeIfPresent`).
- Queue files persisted before v0.6.1 decode without a reset.
- Threaded `externalID` through `StravaUploadTransport.upload(for:from:externalID:)` for background task tagging.

## Key Learnings

1. **Persist before/after pattern is dangerous** — Codable atomicity is not a substitute for state-machine invariants. Check that every persisted state is reachable via some public method.
2. **Background URLSession requires file bodies** — in-memory multipart won't survive suspension. Test this locally: background config + suspend-and-kill simulation.
3. **409 Duplicate is your friend** — idempotency unlocks resilience patterns (retry orphans, confirm async uploads).
4. **Polling with max-attempt gates** — prevents infinite loops on stuck Strava processing; budget → reclaimable `.pending` is the bridge to re-POSTing.
